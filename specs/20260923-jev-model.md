# JobFit — Typed-Decision Model Architecture

## 1. Overview

JobFit's backbone is a repurposed decoder-only causal LLM that answers 17 questions about a CV and
a job description. This document specifies how it produces those answers: each question travels
in the input itself (rather than a fixed output layout decided at training time), and its answer
is read directly off the model's own, unmodified `lm_head` at a dedicated position — no separate
trained scoring head exists anywhere in this design. All 17 questions are answered in one forward
pass, over a sequence structured so each question is evaluated independently of the others despite
sharing that one pass.

The design **deliberately mirrors the public request/response shape of TypeSafe's Jev** ("System
One") decision model — a `state` plus typed `questions` (Score / Choice / Noul) in, one typed
answer per question id out — so the same model and interface can be reused beyond JobFit. The
reference schema is TypeSafe's as published in Cloudflare's `typesafe/jev` model docs
(https://developers.cloudflare.com/ai/models/typesafe/jev/); third-party guides and "reproductions"
are inconsistent and are not relied on. Mirroring the shape is not a claim of behavioral parity:
TypeSafe has not published its architecture, and nothing here clones, executes, or depends on any
TypeSafe or third-party code or service. Deliberate departures from the Jev schema are called out
where they occur (§3 field naming, §4 Score confidence).

**Terminology.** This spec uses Jev's vocabulary: the **state** is what is being evaluated (for
JobFit: CV + JD), a **question** is one typed thing asked about it, an **answer** is the typed
result for one question id. What `specs/20260918-mvp.md` calls the 17 "aspects" are the 17
questions here (same ids, same semantics); `aspects.json` becomes `questions.json` (§3).

## 2. Backbone: a cross-encoder with a shared state and independent question branches

The backbone (SmolLM2-135M-Instruct by default, or Qwen3-0.6B / Llama 3.2 1B / MiniCPM5-2B /
Qwen3.5-4B) is decoder-only — one causal
transformer stack, no separate encoder module, no added parameters anywhere in this design. CV and
JD form a shared **state** segment: concatenated into one sequence and processed under ordinary
causal attention, so JD tokens (placed after the CV) attend over the whole CV.

Each of the 17 questions is then a **branch** off that state (branch is the attention-mask
implementation term only; at the interface level it is simply a question): its question text plus
one answer position, attending back over the state but never over any other question's branch.
This is what makes "one forward pass" and "questions evaluated independently" compatible — instead
of running 17 separate forward passes from a shared, cached state (correct, but expensive in
orchestration) or one plain causal sequence (cheap, but question 17 could attend back over
questions 1-16's text — a real leakage a true independent evaluation wouldn't have), the whole
state+branches structure is computed as **one forward pass using a custom block-diagonal attention
mask**: the state portion is ordinary causal self-attention; each branch attends to the state and
causally to itself, masked off from every other branch. This is mathematically equivalent to 17
independent forward passes sharing a prefix, at the cost of one masked forward pass instead of 17
unmasked ones. It also matches Jev's documented behavior that all questions in a request are
evaluated in parallel and adding questions barely changes latency.

This needs a non-default attention mask (and per-branch position ids restarting at the end of the
state). It is built **inside the model graph** (`pipeline/jev_model.py`'s `JevModel`) from a
per-token `segment_ids` input (−1 padding, 0 state, k for branch k): key j is visible to query i iff
`j ≤ i` and `segment_ids[j] ∈ {0, segment_ids[i]}`, and each token's position id is the number of
tokens visible to it minus one. Training and the exported ONNX graph therefore share one
implementation, and callers only pass 1D inputs (`input_ids`, `segment_ids`, `answer_positions`,
`candidate_ids`); the graph returns `answer_logits` (B, Q, candidates). Verified: a packed pass
equals running each branch alone (tiny Qwen3/Llama tests), and the int8 ONNX export runs unchanged
under transformers.js' generic `PreTrainedModel`, which passes custom-named inputs through.

**Hybrid backbones.** Qwen3.5-4B's config interleaves linear-attention (Gated DeltaNet) layers with
full attention (`full_attention_interval: 4`); linear-attention layers carry a recurrent state and
cannot honor a custom mask. A backbone whose `config.layer_types` contains anything but
`full_attention` therefore runs as one plain causal pass instead (2D padding mask, default
positions): same encoding and interface, but each branch also sees the branches before it (fixed
order, identical in training and inference) — not independent evaluation. See §9.

## 3. Questions: three types, one mechanism, request-defined answer spaces

### 3.1 Sequence layout

```
<state: CV tokens, JD tokens; truncated as a whole to 3072><questions block, budget 1024>
```

Sequences are padded to 4096 tokens (the state budget plus the questions budget). The state is an
ordered `{title: text}` mapping, truncated as a whole to the state budget (only its last part is
cut); JobFit's is `{"CV": cv, "Job description": jd}`, in that fixed order. There is no separate
company input — whatever the JD says about the company is simply part of the JD text. Everything is
rendered as Markdown; the state as

```
# CV
<cv text>

---

# Job description
<jd text>
```

(the headers count inside the state budget), and every question branch, tokenized on its own, as

```


---

# Question
<question text>

# Criteria
0 = <criteria[0]>
1 = <criteria[1]>
...

# Answer
```

The rendering is internal, not part of the interface. The answer prompt ends in a newline, so a
candidate is a bare token after it: the digits `0`–`9`, the letters `A`–`J` and `true`/`false` are
each exactly one token after `"# Answer\n"` on Qwen3 (measured; Llama 3.2 not yet checked, see §9).
The questions block never truncates question text: a question set over its budget is an error. The
17 JobFit questions measure 931 tokens on Qwen3-0.6B (953 on MiniCPM5-2B, 964 on Qwen3.5-4B).

The branch's last token (the newline after `# Answer`) is the position the model would next generate
a token at — no actual generation happens; the model's `lm_head` is simply evaluated at that position, exactly as it would
be during ordinary next-token training. Its output is restricted to a small set of candidate tokens
(renormalized over just those) that **the question itself defines, not the architecture**:

- **Score** — an ordered scale. `criteria` is an array of 2–10 ordered level descriptions (Jev's
  own limit); level `k` is rendered as the digit `k`, so the candidates are the digit tokens
  `0`…`K−1` and K ≤ 10 falls out of the single-digit rendering. All 17 JobFit questions use this
  type, with 5 levels each today — a per-question choice, not an architectural constant.
- **Choice** — an unordered, closed option set: `criteria` is an object of 2–10
  `{key: description}` options, rendered as lettered options `A`, `B`, …, restricted to the letter
  tokens and mapped back to the keys — the standard technique for LLM multiple-choice evaluation.
  Implemented, not used by any current JobFit question.
- **Noul** — a true yes/no proposition: `criteria` is `{true: description, false: description}`,
  restricted to the two candidate tokens `true`/`false`; the answer is P(true). Implemented, not
  used by any current JobFit question (see §6 for why).

All three are the same mechanism — one marker, `lm_head` evaluated there, restricted/renormalized
over that question's own candidate tokens — differing only in what those candidates are and how
the restricted distribution is reduced to an answer (§4). Candidate token ids are an input of the
graph, so the exported model answers any question set. Encoding asserts that every candidate
encodes to exactly one token after the answer prompt for the backbone in use.

### 3.2 `questions.json`

`questions.json` (replacing `aspects.json`, one source of truth) is an object keyed by question id,
shaped like Jev's `questions` request field. It is an internal file, so JobFit's own metadata
(`name` for the UI, `scope` for which state parts the question concerns) sits flat alongside the
Jev fields:

```json
{
  "skills_match": {
    "type": "score",
    "name": "Skills match",
    "scope": "pairwise",
    "question": "How well do the candidate's technical skills cover the technical skills the job requires?",
    "criteria": ["Almost none of the required skills", "A few, with major gaps",
                 "About half", "Most, with minor gaps", "Essentially all"]
  }
}
```

- **One departure from Jev naming:** the question text field is `question`, not Jev's
  `instructions` — the latter is too general for what is, in every case, the question being asked.
  An adapter translating to/from the literal Jev request is a one-field rename.
- Question text follows Jev's own guidance: ask one thing per question, and word it literally (the
  model answers the question as written). `cv`/`job`-scope questions ask about that one document.
- The old `description` field is dropped. The LLM judge (`data/label_pairs.py`, and the clarity
  judge in `data/label_docs.py`) builds its prompt from the same `question` + `criteria` and sees
  exactly what the model sees (CV + JD, no frontmatter company name), so judge and model share one
  rubric; it answers a (possibly fractional) level, stored as `level/(K−1)`. The two descriptions
  that were design notes rather than questions move here:
  - `interview_readiness_score` is an ordinary graded Score question (not a categorical
    Low/Medium/High), consistent with every other question.
  - `culture_company_alignment_score` is only meaningful when the JD itself says something about
    the company (mission, culture, values); otherwise its answer simply has low confidence and
    reads "insufficient data" through the ordinary path (§4) — no separate on/off mechanism.

CV/JD truncation and the questions block's length are logged by `prepare`.

## 4. Answers, confidence, and calibration

The interface mirrors Jev: `evaluate(state, questions) → {answers: {<id>: answer}}` (plus the
model id), as an in-process function in the pipeline and a browser-side call in the frontend — no
HTTP server. Restricting and renormalizing `lm_head`'s output at a marker gives a small probability
distribution over that question's candidates; its reduction to an answer depends on type:

- **Score**: `{type: "score", score, confidence, probabilities}`.
  - `score = Σ_k P(k)·k` — the probability-weighted **0-based level index**, as in Jev (e.g. 1.27
    reads "mostly level 1, leaning toward level 2"). `probabilities` is keyed by the index string.
    Jev's `legend` (index → criteria text) is omitted: the caller already holds the criteria.
  - `confidence = 1 − σ/σ_max`, where `σ` is the standard deviation of the level index under
    `probabilities` and `σ_max = (K−1)/2` (the largest possible spread: half the mass on each end).
    **This deliberately departs from the confidence formula reverse-engineered for Jev from
    TypeSafe's published example, `(K·max_p − 1)/(K − 1)`.** That formula ignores level order: with
    §5's two-hot training, a correct answer between two levels is a 50/50 split over adjacent
    levels, which `max_p` rates 0.375 — as uncertain as a genuinely confused model. The ordinal
    form keeps the two apart. Worked examples, K=5: all mass on one level → 1.0; 50/50 over
    adjacent levels (σ=0.5) → 0.75; uniform (σ=√2) → 0.29; 50/50 over levels 0 and 4 (σ=2) → 0.
- **Choice**: `{type: "choice", choice, confidence, probabilities}` — as in Jev; `choice` is the
  argmax key and `confidence = (K·max_p − 1)/(K − 1)` (appropriate here: options are unordered).
- **Noul**: `{type: "noul", noul}` — P(true), as in Jev. No separate confidence field: distance
  from 0.5 already is the certainty.

**Confidence replaces the interval.** The earlier (score, low, high) interval existed to drive
"insufficient data" and to display a range; a single ordinal confidence per answer does the first
job directly and makes the second unnecessary. There is no conformal `delta` anymore.

**Calibration is generic, not per question.** Jev exposes no calibration parameters, and questions
are defined per request, so per-question parameters could never cover a new question. On the
`calib` split:
- **Model-level:** one scalar temperature `T`, fit to minimize the NLL of `softmax(logits / T)`
  (each question restricted to its own candidates) against the two-hot targets, pooled over every
  question. It ships with the model and applies to every question of every type.
- **JobFit app-level:** one confidence threshold, the nearest-rank 10th percentile of the pooled
  temperature-scaled calib Score confidences. An answer reads **"insufficient data" when
  `confidence < threshold`** — confidence alone decides, with no per-question special-casing.

`calibration.json` is `{temperature, confidence_threshold}`; without a fit (no calib data) the
temperature is 1 and every answer reads "insufficient data" (never fabricate a confident answer
calibration could not back up). Calibration quality is reported as confidence-vs-error instead of
interval coverage: per question, mean `|score − target|` in five equal-width confidence bins, the
Spearman correlation between confidence and `|error|` (should be clearly negative), and the
insufficient-data rate.

**Frontend contract.** The frontend consumes `answers.<id>` directly: it shows `score` on that
question's K-level scale, labeled with the nearest level's criteria text, together with
`confidence`, or "insufficient data" below the threshold. This replaces the low/high interval columns
and the width-based `isInsufficientData(low, high, threshold)`.

## 5. Training

**Data is unchanged.** Labels stay the judge's continuous `<id>_score ∈ [0,1]` plus confidence. At
prepare, a label `y` becomes the target index `t = y·(K−1)`, encoded as a **two-hot** soft target over
the neighbouring levels: mass `1 − (t − ⌊t⌋)` on `⌊t⌋` and `t − ⌊t⌋` on `⌈t⌉`, so the target's
expected index equals `t` exactly (a hard nearest-level target would round away up to half a level
of label precision and bias `score` toward level centres). Judge confidence is used exactly as
today, as a per-target loss weight with the same confidence-floor hard mask. Loss is
confidence-weighted soft cross-entropy over each question's restricted candidate-token softmax,
summed across all 17 questions in one packed, masked forward/backward pass (§2's block-diagonal
mask applies during training too). Choice/Noul train identically (soft cross-entropy against a one-hot option
or `[P(true), 1 − P(true)]` target over their own candidates); JobFit's data has no such question.

**No `headtrain` stage — replaced by `zeroshot`.** With no separate head, a backbone-frozen stage
has nothing to train: the only candidate is `lm_head`, and it is tied to the input embeddings in
Qwen3-0.6B, Qwen3.5-4B (both verified in their configs) and Llama 3.2 1B, so the frozen-backbone
stage would have zero trainable parameters, and unfreezing `lm_head` would change the embeddings
and trip the backbone-hash assertion. (MiniCPM5-2B's head is untied, but one uniform recipe across
backbones is worth more than a head-only stage for one of them.) Instead, **`zeroshot` evaluates
the prompted base model with no training and no checkpoint** — same questions, same mask, same
readout. It is the third baseline after train-mean and keyword-overlap, and the one that measures
what finetuning actually adds; it also directly tests the question and criteria wording, which
matters most with no training. `finetune` (LoRA) starts from the base weights; with a `val` split it keeps the epoch with the
lowest val loss (the same weighted soft cross-entropy), otherwise the last one.

Argo DAG: `prepare → evaluate(zeroshot) → finetune → evaluate → calibrate → evaluate → export →
evaluate → publish`. The weight-hash-unchanged assertion remains around `calibrate` only (it fits
the temperature and threshold, never weights). The eval/report stage labels are `zeroshot`,
`finetuned`, `calibrated`, `quantized`.

## 6. Generalization, and its limits

The mechanism is fully generic: a Score, Choice, or Noul question all become just another branch
off the same state, read out via the same unmodified `lm_head`, with zero architecture or weight
change — only the questions block's text (and that question's candidate tokens) changes. This is
what makes the Jev-shaped interface reusable beyond JobFit. It is distinct from zero-shot
competence: the model is trained on JobFit's specific 17 Score questions, and needs task-specific
training data before being trusted on a materially different question, including any Choice- or
Noul-type question this document defines the mechanism for but which JobFit itself never trains or
calls. The `zeroshot` stage (§5) quantifies exactly this gap for JobFit's own questions.

**Is Noul a better fit for JobFit's own questions?** No — but not because Noul would discard
gradation: a Noul answer trained against soft targets is a continuous P(true) and could carry the
graded judge score. The real reason is **uncertainty**. A two-point distribution cannot tell
"confidently middling fit" from "no idea" — both are P(true) ≈ 0.5 — and JobFit's product
contract depends on exactly that distinction (answer vs. "insufficient data"). A Score distribution
over ordered levels keeps them apart (mass concentrated near one level vs. spread across the scale,
§4's ordinal confidence). Jev's own guidance points the same way: Noul is for true yes/no
propositions, not a disguised intensity scale. Even the closest candidates — questions #14/#15
(LLM-generated-content likelihood), which really are a single detector probability under the hood —
are specified as Score like every other question, and `specs/20260918-mvp.md` §8 explicitly rules
out per-question special-casing; carving out a Noul exception for just those two would reintroduce
exactly the special-casing that section rejects. Noul and Choice are included purely for the
generality asked of this architecture, not because JobFit's current task needs them.

## 7. Non-goals

- No dependency on, or behavioral-parity claim with, TypeSafe's service or any third-party
  "typed decision" system, benchmark, corpus, or code. The request/response *shape* is mirrored
  intentionally (§1); nothing else is.
- No HTTP server or network-exposed inference — scoring stays entirely client-side and
  non-generative; `evaluate(state, questions)` is an in-process/in-browser call.
- No change to the 17 questions' ids or semantics, or to the label/data schema.
- JobFit neither trains nor calls Choice- or Noul-type questions. The mechanisms are implemented in
  the generic core (encoding, targets, readout, in Python and JS) and checked end to end by the
  export's parity fixture, so the model is reusable beyond JobFit.
- No new trained parameters beyond LoRA — deliberately, since the whole point of this design is to
  reuse the model's native `lm_head`. Nothing is trained before `finetune`.
- Jev's context limits (32k state + longest question; 64k total) are not a target; this model stays
  at 4096 tokens (3072 state + 1024 questions).

## 8. Relationship to `specs/20260918-mvp.md`

This document supersedes that spec's CQR-head subsection of §4, the parts of §6/§10 that describe
it, and the `headtrain` stage and its "linear probe" checkpoint (those sections carry a banner
pointing here). It also changes how the model is loaded throughout: always `AutoModelForCausalLM`
(native `lm_head` intact), never `AutoModelForSequenceClassification`.

Beyond the model itself, it changes:
- `aspects.json` → `questions.json` (§3.2), and "aspect" → "question" in code identifiers; the
  label columns (`<id>_score`, `<id>_confidence`) keep their names since ids are unchanged.
- The judge prompt (`data/label_pairs.py`, and the clarity judge in `data/label_docs.py`)
  is built from `question` + `criteria`.
- The frontend contract: Jev-shaped `answers` with `score`/`confidence` replace (score, low, high);
  `calibration.json` becomes one model-level `{temperature, confidence_threshold}` (§4).
- Evaluation: per-question MAE and Spearman ρ are computed on `score/(K−1)` against the `[0,1]`
  labels; interval coverage/width is replaced by confidence-vs-error (§4).
- Stages: `headtrain` removed, `zeroshot` evaluation added (§5); `finetune` keeps the best epoch
  by val loss rather than mean per-question val MAE.

Everything else in that spec is unchanged: §1's backbone/causal trade-off, §2's product non-goals,
§3's 17 aspects (now questions), §5's data/label schema, and §6's pipeline stage structure apart
from the `headtrain` change. §7's frontend latency budget (<5s WebGPU / <30s WASM) should be revised
to **<6s WebGPU / <40s WASM**, reflecting the longer sequence (2048→4096 tokens) — a
pre-implementation estimate, not re-measured at 4096, not a measurement.

**Implementation.** The generic core is `pipeline/jev.py` (rendering, encoding, candidate tokens,
targets, readout, temperature fitting), `pipeline/jev_model.py` (the masked `JevModel`, loss,
in-process `evaluate`) and their exact JS mirror `frontend/src/jev.mjs` (encoding, readout);
`frontend/scripts/verify-parity.mjs` checks the mirror against the pipeline's export. JobFit's own
parts are `questions.json` (loaded by `data/corpus.py`), the label joining in `pipeline/common.py`,
the judge rubric (`data/rubric.py`) and prompts, the metrics/report, and
`frontend/src/{jobfit.mjs,scoring.ts,App.vue}`.

## 9. Open questions

- Real-browser WebGPU/WASM runs of the int8 export (§2) remain to be measured; it is verified only
  on Qwen3-0.6B against the pinned ONNX Runtime 1.21 in Node.
- Qwen3.5-4B (hybrid linear attention, §2) runs without branch isolation. Not yet runnable at all:
  transformers 4.57 (the version the pipeline runs with) has no `qwen3_5`, and ONNX export of Gated DeltaNet layers is
  unproven. Its report must be read with the leakage caveat in mind.
- Questions-block budget: the 17 questions measure 931/1024 tokens on Qwen3-0.6B (964 on Qwen3.5-4B, the
  largest). If they grow,
  shorten criteria texts before raising the budget (which would lengthen the sequence and move the latency
  estimate).
- Llama 3.2 1B tokenizer (license-gated, not cached locally): confirm the full candidate set —
  digits `0`–`9`, letters `A`–`J` and `true`/`false` — is single tokens after `"# Answer\n"`, as it
  is for the other three backbones.
- Whether to relabel existing data with the new shared judge rubric (§3.2). Default: keep existing
  labels — they are on the same `[0,1]` scale — and use the rubric for new labels only.
- Whether/when a genuine Choice- or Noul-type JobFit or adjacent use case actually materializes —
  nothing here should be built out further until one does.
- Standard LLM multiple-choice evaluation has known option-order-bias effects for Choice-type
  questions; not exercised by JobFit's Score-only questions today, worth a mitigation note if a
  Choice-type question is ever actually added.
- Noul's candidate tokens (`true`/`false`) are single tokens after the answer prompt on Qwen3; real
  usage may still need casing/synonym handling once a Noul question actually exists.
- The pooled confidence threshold treats all questions alike; if some questions turn out
  systematically over- or under-confident after temperature scaling, that is a model-quality
  finding to fix in training data, not with per-question parameters.
