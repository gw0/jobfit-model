# JobFit — MVP Specification

## 1. Overview

JobFit is a CV/job-description fit-scoring web app. Its core model is a small, **non-generative scoring model** — the backbone of a pretrained open-weight decoder-only LLM, repurposed via Hugging Face's `AutoModelForSequenceClassification(problem_type="regression")` — fine-tuned with LoRA, explicitly calibrated, and quantized to run entirely client-side in the browser.

Note the backbone stays **causal**, not bidirectional: only the final token attends to the whole input, and that token is what the regression head pools. This is a deliberate trade (it buys a strong pretrained initialization and a well-supported export path) and a known limitation versus a true encoder.

The project demonstrates a complete, real MLOps lifecycle end to end: model repurposing (not training from scratch), parameter-efficient fine-tuning, post-hoc calibration, quantization, multi-model benchmarking, a Kubernetes-based training pipeline, and edge (in-browser) deployment.

This MVP covers the **entire scope** described below — it is not a reduced first cut.

## 2. Goals / Non-goals

**Goals**
- A public web app where a user pastes/uploads a CV + job description and receives a set of continuous, calibrated scores.
- A public benchmark report (accuracy/calibration vs. non-learned baselines, across the four candidate models, at each training stage, before/after quantization, latency and size).
- Fine-tuning/eval code and Kubernetes infrastructure-as-code, shareable publicly.

**Non-goals** (product scope; rejected *aspects* are in §3, rejected *tooling* in §11)
- **No server-side inference.** All scoring happens in the user's browser. There is no inference API, no account, no persistence.
- **No generative output.** Every result is a number with a confidence interval — never free text, never a rewritten CV, never advice prose.
- **No data collection.** There is no always-on, publicly-reachable service collecting user data, and no opt-in prompt asking users to contribute theirs.

## 3. Scored aspects

Every output is a **continuous score + confidence interval**. Low-confidence predictions surface as **"insufficient data"** in the UI rather than a fabricated mid-range score.

| # | Aspect | Scope | Notes |
|---|--------|-------|-------|
| 1 | Skills match | pairwise | Technical/hard-skills overlap between CV and JD |
| 2 | Experience level match | pairwise | Years of experience vs. JD requirement |
| 3 | Domain/industry relevance | pairwise | CV's industry background vs. JD's industry |
| 4 | Education/qualifications match | pairwise | Degree level/field vs. JD requirements |
| 5 | Seniority/role-level fit | pairwise | IC vs. lead/manager, title alignment |
| 6 | Career trajectory fit | pairwise | Whether the role is a natural step for the candidate's history |
| 7 | Responsibilities overlap | pairwise | Past-role duties vs. JD's responsibilities |
| 8 | Location/work-arrangement fit | pairwise | Remote/hybrid/onsite and location compatibility |
| 9 | Soft-skills match | pairwise | Soft skills the JD asks for vs. evidence for them in the CV |
| 10 | Recency of relevant experience | pairwise | How recent the JD-relevant experience is |
| 11 | CV clarity/structure quality | cv | CV text structure/parseability, independent of any JD |
| 12 | Job post clarity/structure quality | job | JD text structure/clarity |
| 13 | Overall Fit Score | pairwise | Composite CV-to-JD semantic fit |
| 14 | CV likely LLM-generated | cv | Labeled via an existing open-source AI-text-detector's raw score |
| 15 | Job post likely LLM-generated | job | Same detector-based labeling, applied to JD text |
| 16 | Interview-Readiness Score | pairwise | Continuous (not the categorical Low/Medium/High originally considered), consistent with every other aspect |
| 17 | Culture/company-alignment score | pairwise | Only meaningful when the JD itself says something about the company; otherwise the predicted interval is simply wide and reads "insufficient data" through the ordinary confidence path — no separate on/off mechanism |

**13 pairwise / 4 single-document** (`cv`: #11, #14; `job`: #12, #15). The model always takes the full CV+JD input and predicts all 17 aspects in one forward pass — the scope distinction only affects how labels are stored (§5), not the model's I/O shape.

**Rejected aspects**: a separate rule-based "ATS Compatibility Score" (non-ML and redundant with #11); salary/comp-expectation alignment; a free-text "company snapshot" (replaced by trained aspect #17).

**Cross-cutting eval check**: a shuffled/mismatched CV–JD control (pairing a CV with an unrelated JD) confirms per-aspect scores respond to actual input content rather than superficial priors (JD length, keyword density) — logged to MLflow alongside `test`-split metrics.

**Score semantics**: a raw score is not a probability. Every threshold built on one — including the "insufficient data" cutoff — comes from the per-aspect calibration fit (§4), never assumed at 0.5.

## 4. Model

> **Superseded in part by [`20260923-jev-model.md`](20260923-jev-model.md)**: the CQR head, pinball loss, `headtrain` stage, conformal calibration, interval metrics and `AutoModelForSequenceClassification` loading are replaced by the typed-decision model (questions answered by the native `lm_head`, two-hot training, `zeroshot` evaluation, temperature + confidence-threshold calibration, `max_length = 3072`). The candidate table, baselines, JevBench and reproducibility points still apply.

- **Backbone**: repurposed from a pretrained open-weight decoder-only LLM via `AutoModelForSequenceClassification` — no custom modeling code.
- **Candidates (locked)**:

  | Candidate | Base licence | Notes |
  |---|---|---|
  | Qwen3-0.6B | Apache-2.0 | The expected shipping candidate |
  | Llama 3.2 1B | Llama Community License | Attribution + acceptable-use terms follow the Hub artifact and the browser bundle |
  | MiniCPM5-2B | per model card | Verify before locking |
  | Qwen3.5-4B | Apache-2.0 | Accuracy ceiling; see the size risk below |

  **Prerequisite for any candidate**: the HF repo ID must exist, `optimum` must export it to ONNX, *and* transformers.js must have a matching JS tokenizer and model class. Verify all four before starting — `MiniCPM5-2B` and `Qwen3.5-4B` in particular.

  **Size is a benchmark column, not a gate.** Quantized weights run from ≈0.6 GB (0.6B int8) to ≈4 GB (4B int8) / ≈2.2 GB (4B q4), against an ORT Web practical WASM heap of ~2 GB; ONNX files over 2 GB need external-data format, which transformers.js handles awkwardly. The larger candidates may turn out to be trainable and evaluable but not loadable in a browser — that outcome is a reportable finding (§10), not a surprise.

- **Head — conformalized quantile regression (CQR)**: the head predicts **3 quantiles (0.05 / 0.5 / 0.95) per aspect**, so `num_labels = 17 × 3 = 51`, trained with pinball loss. The 0.5 quantile is the reported score; the conformalised 0.05–0.95 interval is the confidence. Plain scalar regression was rejected because a single conformal interval per aspect has the *same width for every input* and therefore cannot express "low confidence for this particular input" — which §3 and §9 both require.
- **Input encoding**: `max_length = 2048`, with CV and JD each given a fixed 1024-token budget and truncated independently, rather than truncating the tail of one concatenated string (which would silently drop the JD entirely for long CVs). **JD goes last**, since under causal attention only the final tokens see the full input. Truncation rate is logged as a dataset metric.
- **Loss masking**: targets are NaN-able and the pinball loss ignores NaN positions. Aspect #17 is unlabeled whenever a pair has no company info, and single-document labels join onto pairs from two separate files — neither case may contribute gradient. Judge-reported label confidence (§5) is used as a per-target loss weight, and targets below a confidence floor are masked out entirely; it is never a prediction target.
- **Training, per candidate, two explicit stages** (linear-probe-then-fine-tune practice):
  1. **`headtrain`** — train only the quantile head, backbone frozen (no LoRA yet). A meaningful baseline checkpoint in its own right, not just an initialization step.
  2. **`finetune`** — unfreeze and continue training end-to-end via LoRA (HF `peft`), starting from the `headtrain` checkpoint. Deliberate per-architecture LoRA target-module selection (attention + MLP projections), not defaults. Adapters merged (`merge_and_unload()`) before export, so the exported model is a plain dense model.
- **Hyperparameter experimentation**: manual/scripted re-runs per candidate (different LoRA rank/alpha/lr, etc.), exposed as Argo workflow parameters.
- **Calibration**: conformalise the predicted quantiles on the `calib` split to a **90% target coverage**, fit independently per aspect — each aspect has its own raw-score scale, so one shared mapping would be wrong. The same fit yields the per-aspect interval-width threshold above which the UI shows "insufficient data". ECE is not used; it is classification-native.
- **Calibration and quantization are separate, sequential stages** (`calibrate` runs before `export`/quantize, §6). The mapping is fit once on the fine-tuned model, then the post-quantization `evaluate` pass applies it **unchanged** and reports whether quantization measurably breaks the calibration guarantees — a genuine finding for the benchmark report, not something to silently patch over. Separately, and only for the **shipped** artifact, the conformal mapping is re-fit on the quantized model's `calib` outputs, so users are not served intervals the report itself shows to be broken. Re-fitting is a quantile computation over cached outputs: no retraining, minutes of CPU. Both the post-quantization `evaluate` and the re-fit run on the same ONNX Runtime release that transformers.js bundles: int8 kernels differ between releases by more than the whole label range on identical inputs, so any other runtime would measure a different model than users run.
- **Baselines — two, both non-learned**:
  1. **Per-aspect `train`-split mean.** The trivial floor. A model that does not beat it has learned nothing, and no other number in the report means anything until this one is cleared.
  2. **CV/JD embedding cosine similarity** (or keyword-overlap ratio), mapped to each aspect through a per-aspect linear fit on `train` — one scalar cannot otherwise produce 17 predictions.
- **Metrics**: quality is **per-aspect MAE + Spearman ρ** (rank correlation is what a fit score is actually used for); calibration is **empirical coverage at the 90% target + mean interval width**. The single scalar for `load_best_model_at_end` is **mean per-aspect MAE on `val`**.
- **Side-eval — JevBench** (`fstandhartinger/jevbench`): an informational drift/forgetting check, not used for model selection or comparative claims. Run **twice**: once on the base pretrained weights as a reference, once after `finetune`. Because `AutoModelForSequenceClassification` drops the `lm_head`, the post-`finetune` run requires rebuilding a causal LM — re-load the base `AutoModelForCausalLM` and apply the same LoRA adapters to it. This is the only non-trivial part of the side-eval.
  Backbone integrity after `headtrain` and `calibrate` is asserted with a **SHA-256 hash of the backbone state dict** rather than a JevBench run: neither stage touches backbone weights, so an exact hash comparison is instant and a strictly stronger test of the freezing logic than comparing benchmark scores.
- **Reproducibility**: seeded (`torch.manual_seed` + numpy/random, logged as an MLflow param); `load_best_model_at_end=True` tied to the metric named above; mixed precision/`torch.compile` treated as a benchmark question, not assumed as a free win on CPU.

## 5. Data

Dataset construction is an **offline, one-time, versioned toolset** — separate from the recurring Kubernetes pipeline (see §6 for why), and its output is **committed directly to this repository**.

- **CVs are entirely synthetic.** No real CVs are collected, labeled, or committed. They are LLM-generated directly as plain Markdown in already-"parsed" form — no PDF is rendered or parsed during dataset construction. Real user uploads at inference time still go through actual PDF text extraction in the browser (§7); training data skips that round trip and is written straight to the format the model consumes (see §11 for the residual risk this leaves).
- **Job-post retrieval**: from job boards, via `data/fetch_jobs/` (Greenhouse, Lever, Ashby and Workday adapters, plus HN Who's Hiring / RemoteOK / WeWorkRemotely discovery). Posts are written as Markdown with a YAML frontmatter block (`company`, `title`, `location`, `url`, `posted_at`) — provenance metadata and the dedup key, never scores.
- **Labeling**: an LLM-as-judge directly scores each of the 15 judged aspects (0–1, with a confidence) for every (CV, JD) pair. The 2 LLM-generated-content aspects (#14, #15) instead use an existing open-source AI-text-detector's raw score, applied once per document.
- **Label quality control**: a sample of the `test` split is double-labeled by a second, stronger LLM (the bulk pass runs on Sonnet, the QC pass on Opus) once, during dataset construction, to check inter-rater reliability on the labels themselves. This is why there is no separate LLM-judge pass at eval time (§6) — the reliability check already happened at label-creation time.
- **PII scrubbing**: Microsoft Presidio, as a safety net over LLM-generated text (generators do emit real-looking names and occasionally real ones). With no real CVs in the corpus it is not scrubbing anyone's personal data, but it stays: it is cheap, and `prepare` (§6) asserts on it.
- **Targets** (`datasets_full/`; `datasets_smoke/` is a 10-CV/10-job logic check): 250 synthetic CVs, ~400 job posts (≤10 per company), and 5,000 labeled pairs, 20 per CV, sampled from the ~80k possible combinations: half the CV's nearest jobs by TF-IDF cosine, half uniformly at random, so the fit labels span the whole scale rather than piling up at "no fit". That gives `calib` = 500 pairs, which the conformal quantiles need. Repo size ceiling ~100 MB — above that the dataset moves to a HF dataset repo.
- **Splits — `train` / `val` / `calib` / `test`**: grouped by CV identity, so paraphrased/variant synthetic CVs of one underlying profile stay in a single split (LLM generation raises near-duplicate risk). `test` is additionally **disjoint on both axes** — no CV *and* no company appearing in `train` — because leaving a job post in both splits lets the model memorize that post's per-aspect tendencies and inflates `test` scores. Some pairs get dropped; that is the correct cost.
- **Known limitation**: 250 CV profiles split four ways puts roughly 25 distinct CVs in `test`. Pair counts stay healthy since each CV pairs with many JDs, but generalisation *to unseen candidates* rests on ~25 profiles and per-aspect `test` metrics will be noisy across reseeds. Mitigated by a fixed split seed and by reporting `test` metrics with bootstrap confidence intervals over CV groups; stated plainly in §10.

**Dataset storage** — committed under `datasets_<SCALE>/` (kept separate from `data/`, which holds the build *scripts*, not the built data). Raw text and scores are kept strictly apart: raw files hold no scores, and labels never duplicate raw text — they reference it by path.

```
datasets_<SCALE>/
├── cvs/
│   └── <name>.md                      # one synthetic CV, no scores
├── jobs/
│   └── <company>/
│       └── <YYYYMMDD>-<job-title>.md  # one job post: YAML frontmatter + body, no scores
├── labels/
│   ├── cvs.jsonl        # {cv, cv_clarity_structure_quality_score/_confidence, cv_likely_llm_generated_score/_confidence}
│   ├── jobs.jsonl       # {job, job_post_clarity_structure_quality_score/_confidence, job_post_likely_llm_generated_score/_confidence}
│   └── pairs.jsonl      # {cv, job, <13 pairwise aspect scores + confidences>, labeling_method}
└── splits/
    ├── train.jsonl      # list of {cv, job} pairs in this split
    ├── val.jsonl
    ├── calib.jsonl
    └── test.jsonl
```

Each raw file's own relative path (e.g. `cvs/jane-doe-042.md`, `jobs/acme-corp/20260615-senior-backend-engineer.md`) **is its ID**, used as-is in the `cv`/`job` fields. No separate numeric/UUID scheme: one place holds the text (`cvs/`, `jobs/`), one place holds the scores (`labels/`), and nothing needs keeping in sync beyond that path. `labels/cvs.jsonl` and `labels/jobs.jsonl` hold each document's single-document aspects (#11/#14 for CVs, #12/#15 for job posts); `labels/pairs.jsonl` holds the 13 pairwise ones. Everything is plain Markdown/JSONL — no PDFs — small enough to commit directly.

## 6. Pipeline & orchestration

> **Superseded in part by [`20260923-jev-model.md`](20260923-jev-model.md)**: `headtrain` → `evaluate` [headtrained] is replaced by `evaluate` [zeroshot] on the base model; `finetune` starts from the base weights.

**Two-tier structure**, deliberately separated:

1. **Offline dataset-build toolset** (§5) — not part of the recurring Kubernetes pipeline. LLM-judge calls are costly and non-deterministic; re-running them on every pipeline execution would break the reproducibility properties designed into the rest of the system (seeded runs, git-SHA tagging). The toolset writes into the committed `datasets_<SCALE>/` directory.

2. **Argo Workflows DAG** (orchestrator; not Kubeflow Pipelines, not Ray — both disproportionate for this scale):
   - `prepare` (once) — **verify and materialise, never re-split**. Load the committed `datasets_<SCALE>/`, assert the committed splits are leakage-free on both axes, run Presidio as a read-only scan that *fails the run* on a hit, tokenize, and cache tensors. The splits are committed precisely so that runs are reproducible; a stage that re-derived them would make that guarantee meaningless.
   - Per-candidate fan-out:
     `headtrain` → `evaluate` [headtrained] → `finetune` (parameterized for manual hyperparameter experiments) → `evaluate` [finetuned] → `calibrate` → `evaluate` [calibrated] → `export`/quantize (`optimum-onnx`/`ORTQuantizer`) → `evaluate` [quantized]. Every stage that changes the model gets its own eval immediately after it — isolating what fine-tuning contributes (`finetuned` vs. `headtrained`) from what calibration contributes (`calibrated` vs. `finetuned`: accuracy ~flat, calibration metrics improved) from what quantization costs (`quantized` vs. `calibrated`).
     `headtrain` and `calibrate` additionally assert the backbone weight hash is unchanged (§4).
   - `publish` — compare candidates, push the winning model to HF Hub, publish the W&B benchmark report.

**Run results are committed, not just tracked.** `publish` writes a self-contained `runs_<SCALE>/<candidate>/reports/report.json` (plus a rendered `report.md`, the git SHA recorded inside) into the repository, and the benchmark report (§10) and W&B export are assembled from those files. MLflow's store is backed by a hostPath PV that is tied to one host, but §7 provisions the cluster per run and may move between a CPU and a GPU host — so candidates trained on different hosts could not otherwise be compared, which is exactly what the report requires. Committed result files survive host changes and keep one source of truth, with no S3/MinIO.

**MLflow** — runs as a real server (Kubernetes Deployment + Service) inside the training cluster, backed by the hostPath-backed local PV for its file/SQLite tracking store and artifacts. It comes up with the cluster for the duration of a training run and is torn down with it — not always-on, but a proper server process rather than direct file access from each pod. Scoped to training-run tracking and model registry. Best practices demonstrated: autologging (the HF `Trainer`'s MLflow integration); nested runs (one parent per pipeline execution, one child per stage); dataset lineage via `mlflow.log_input()`; model signatures via `mlflow.models.infer_signature()`; registry aliases (e.g. `champion`); runs tagged with the git commit SHA.

**No separate LLM-as-judge pass at eval time.** `test`-split labels already come from the LLM judge, with reliability double-checked at label-creation time (§5); a second live judge pass on model predictions would mostly re-agree with its own source rather than add signal. Runtime eval stays: predictions vs. judge-derived labels, via the metrics in §4.

**OpenTelemetry** instruments each pipeline stage plus GPU utilization during training, exported to Prometheus/Grafana. **HF Hub** distributes the winning model (`push_to_hub()`). **W&B** publishes the public benchmark report (a small scripted export; no native MLflow↔W&B bridge exists).

## 7. Infrastructure

- **Cluster**: a single-node **KinD** cluster, provisioned on demand for each training pipeline run and torn down afterward. There is no persistent, always-on cluster or service — nothing in this MVP needs one, since there is no live data-collection service. The same KinD manifests serve a local dev/test execution and the real run that produces the shipped model — one tool, one set of manifests, invoked per run rather than kept running.
- **Compute**: the host running the cluster is a rented CPU machine by default. When a candidate benefits from GPU — for the CPU-vs-GPU benchmark, and for candidates like Qwen3.5-4B where CPU-only training time is impractical — the same cluster is provisioned on a rented GPU-equipped host for that run. This is a host-selection choice at cluster-creation time, not a live GPU node pool joining a running cluster.
- **Storage**: a hostPath-backed local PersistentVolume for MLflow's artifact store — not S3/MinIO (a single-node cluster means every pod already shares one host, so object storage would solve a multi-node problem this project does not have). Cross-run comparison does not depend on it; see §6.
- **Frontend hosting**: static SPA on **HF Spaces (Static)**, the primary/locked deployment target (ties the project to train → HF Hub → HF Spaces). `docker/frontend.Dockerfile` (§8) is an additional, optional self-hosted alternative — it does not replace HF Spaces.
- **In-browser inference**: transformers.js (wraps ONNX Runtime Web) for scoring; `pdf.js`/`pdfjs-dist`'s `getTextContent()` for naive, basic text extraction from an uploaded CV PDF (deliberately unsophisticated, to mimic real ATS parsing failure modes — the only place PDF parsing happens in the MVP; see §5).
- **Frontend performance budget** — the two things a user actually experiences, so both are specified rather than discovered:
  - `device: 'webgpu'` with automatic fallback to `wasm`. Target: scoring completes in **< 5 s on WebGPU, < 30 s on WASM** for a 2048-token input.
  - Weights are fetched once and cached (transformers.js Cache API), with a visible download progress indicator on first load. Model download size is shown up front — a first load of several hundred MB must not look like a hang.

- **`questions.json`**, not a Python module: the frontend is a static TS/JS SPA, so a language-agnostic schema (loaded via `import` in the frontend, `json.load` in pipeline code) is the single source of truth for both, avoiding drift. Keyed by question id; per question: `type`, `name`, `scope` (`pairwise` | `cv` | `job`), `question`, `criteria` ([`20260923-jev-model.md`](20260923-jev-model.md) §3.2).
  There is deliberately **no per-aspect "requires optional input" flag**. Confidence alone drives the "insufficient data" display, so the frontend has no aspect-specific branch that can drift out of sync — question #17 for a JD without company information is simply a low-confidence answer.
  The temperature and confidence threshold are *outputs* of `calibrate`, so they are **not** in this file: `questions.json` holds only the static fields in git, and `export` ships the fitted thresholds as `calibration.json` inside the model bundle. Otherwise the pipeline would rewrite its own committed source of truth on every run.
- **`docker/pipeline.Dockerfile`**: one shared Python image (transformers/peft/optimum/mlflow) reused across all Argo pipeline phases via different entrypoint commands — not one image per stage.
- **`docker/frontend.Dockerfile`**: standard multi-stage — build stage (`node:*-alpine`, `npm ci && npm run build`) producing the static bundle, runtime stage (`nginx:alpine`) copying only the built output into `/usr/share/nginx/html`, running as a non-root user, with an SPA-routing fallback (`try_files $uri $uri/ /index.html;`) plus gzip/caching config.

## 9. User-facing flow

User pastes/uploads a CV + job description and receives the 17 calibrated scores with their confidence intervals. Any aspect whose interval is wider than its calibrated threshold shows "insufficient data" instead of a fabricated score; culture/alignment for a JD that says nothing about the company reaches that state through this same general path, not a special case. There is no opt-in/data-collection checkbox.

## 10. Reporting

> **Superseded in part by [`20260923-jev-model.md`](20260923-jev-model.md)**: the four checkpoints are zeroshot / finetuned / calibrated / quantized, and calibration is reported as confidence-vs-error and the insufficient-data rate instead of coverage and interval width.

Public benchmark report across the four candidates:

- **Quality**: four-checkpoint comparison (headtrained / finetuned / calibrated / quantized) against both baselines from §4 — the per-aspect `train`-mean floor first, then the cosine/keyword heuristic.
- **Calibration**: coverage and mean interval width per checkpoint, including the honest un-refit post-quantization numbers.
- **Deployability**, per candidate: quantized bundle size, cold-load time, per-inference latency on WebGPU and WASM, and **whether it loads in a browser at all**.
- **Drift**: JevBench at base and post-finetune (§4).
- **Stated limitation**: `test` covers ~25 distinct CV profiles (§5), so candidate-axis generalisation is the weakest claim here; `test` metrics are reported with bootstrap confidence intervals over CV groups.

**The repository ships no model weights.** Trained models live only on the HF Hub; `.gitignore` carries the weight-file patterns so this holds by construction rather than by discipline. Reproducing the benchmark therefore means the committed dataset plus a Hub pull, not a repo clone alone. Because the dataset is fully synthetic (§5), it is committed without reservation and every number in the report is third-party reproducible.

Base-model licences follow the published artifact, not this repository: a Llama-3.2-derived winner carries Community-License attribution and acceptable-use obligations that attach to the Hub push and the HF Spaces bundle. This is a candidate-selection input (§4), not a footnote discovered after the winner is chosen.

## 11. Deferred / explicitly out of scope for MVP

**Product and method**
- **Ranking-based LLM-judge labeling** (LLM ranks several JDs for one CV, converted to a latent score) — a fallback for aspects where direct 0–1 scoring proves unreliable, but not designed or built for MVP. Revisit only if direct-scored labels show poor consistency.
- **PDF rendering/parsing in the training-data pipeline** — synthetic CVs are generated as pre-parsed text. With no real-CV PDFs in the corpus either, **nothing in the MVP measures the train/inference PDF-parse gap**: the model trains on clean Markdown and, at inference, is handed whatever `getTextContent()` produces from a real PDF. This is the project's largest unquantified assumption, and it is stated rather than implied.
- **Hard-requirement gate flags** and a **cached-judgments/instant-reweight UI** — reasonable product ideas, but frontend/business-logic with no MLOps-skill signal.

**Tooling considered and rejected** (each for one reason, stated once)
- **vLLM** — no generative-serving role; the model is non-generative and fully client-side.
- **LangChain / LlamaIndex / AutoGen** — no agent/RAG orchestration in this architecture.
- **Automated HPO (Optuna)** — manual/scripted re-runs cover MVP hyperparameter experimentation; an easy add-on later.
- **Agentic tool-use, sandboxing, prompt-injection defenses, MCP** — no tool-use loop exists here.
- **Databricks/Snowflake-scale tooling** (Delta Lake, Unity Catalog, Spark, a warehouse), **Ray/KubeRay, Kubeflow Pipelines, S3/MinIO** — dataset and model scale never justify this infrastructure.
- **An opt-in production data collector** — see §2.

## 12. Open questions

- Whether scraped job-post text is redistributable in a public repository, and under which sources' terms. An engineering-level robots.txt/ToS review and the decision for the smoke corpus are in `data/README.md`; a large-scale or commercial corpus still needs a per-ATS legal review. (The fetchers identify themselves with a descriptive, non-browser User-Agent; `make test` guards against a spoofed one.)
- Exact LLM-judge prompt design and choice of judge model(s) — implementation details to settle during build, not spec-level blockers.

## 13. Acceptance criteria

The MVP is done when:

1. **Parity**: a fixed set of sample inputs produces identical token IDs in Python and transformers.js, and scores agreeing within a stated tolerance. This is the likeliest place for a silent train/inference bug and the cheapest to check. `export` records a sample pair with its expected token IDs and scores in the bundle's `parity.json`; `frontend/scripts/verify-parity.mjs` fails on any mismatch (Node/onnxruntime-node — the browser's WASM/WebGPU execution still needs a real-browser check).
2. **The model beats the floor**: the shipped candidate beats the per-aspect `train`-mean baseline on `test` for a clear majority of the 17 aspects.
3. **Calibration holds**: the shipped (re-fit, post-quantization) intervals achieve empirical coverage within a stated tolerance of the 90% target on `test`.
4. **The control passes**: shuffled CV–JD pairs score measurably differently from true pairs (§3).
5. **The pipeline is reproducible**: two runs at the same git SHA and seed produce matching metrics, and `prepare`'s leakage and PII assertions pass from a clean clone.
6. **The app works end to end**: a real PDF CV uploaded to the deployed HF Space returns 17 scores within the §7 latency budget, with "insufficient data" shown where intervals are wide.
