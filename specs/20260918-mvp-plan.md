**Environment gotchas hit during Phases 0-4, worth knowing before re-deriving them:**
- **Nested `claude -p` calls don't inherit auth.** If you (the agent) are running
  inside a Claude Code session's own Bash tool, `claude` subprocess calls you spawn
  yourself fail with "Not logged in" — this is a sandbox boundary, not a bug to work
  around. `data/generate_cvs.py` and `data/label_dataset.py` must be run by the human
  in their own terminal, not by the agent. Write the scripts, hand over exact commands.
- `claude`'s `--json-schema` flag also failed with "Not logged in" specifically (even
  though plain `-p` and `--output-format json` alone worked) in that same nested
  context — root cause unconfirmed, just don't rely on `--json-schema`. Instead:
  `--output-format json` + a prompt instructing "respond with ONLY a raw JSON object"
  + `json.loads(text, strict=False)` (models routinely emit literal newlines inside
  JSON string values, which strict mode rejects) with a fenced-code/brace-scanning
  fallback. See `data/claude_json.py`.
- `data/claude_json.py` shells out via `bash -i -c "claude ..."` (not a direct argv
  exec) so a `claude` shell alias is picked up. That means `~/.bashrc` banner output
  and ANSI cursor codes can land in stdout ahead of claude's own JSON — parse by
  anchoring on the literal `"[{"`/`"}]"` markers (ANSI CSI sequences start `\x1b[` but
  never produce literal `"[{"`), not by assuming stdout is pure JSON.
- This specific sandbox's Python TLS cert bundle can resolve to a masked/null device
  and `~/.cache` can be read-only, needing `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt`
  workarounds for pip/HF downloads. `requests`-based downloaders (e.g. `spacy download`)
  need `REQUESTS_CA_BUNDLE` set to the same path too — `SSL_CERT_FILE` alone isn't
  enough for those. These are this sandbox's quirks, not real repo requirements — don't
  bake them into scripts. For `HF_HOME`, prefer the persistent `.hf_cache/` under the
  repo root (gitignored) over `$TMPDIR/hf_cache` — `$TMPDIR` doesn't survive across
  sessions, and re-downloading multi-GB candidate weights every session is wasteful
  (Phase 7's candidate compatibility checks use this).
- **Docker is unreachable from the agent's sandboxed Bash tool** (`docker.sock`:
  permission denied) — same category as the `claude -p` auth boundary above. Any
  `docker build`/`docker run`/`docker ps` step (Phase 6 on) needs the human to run it in
  their own terminal; the agent can still verify the underlying script logic by
  installing the relevant `requirements.txt` into `.venv` directly and running the
  script un-containerized.
- **Presidio's default `US_SSN` recognizer did not flag a plain `"SSN: 123-45-6789"`
  string** in ad-hoc testing (Phase 6) — a real gap in its default regex/context
  scoring on that exact phrasing, not a bug in `data/pii_scrub.py`'s entity-type scoping.
  A real (non-`@example.com`) email address is the more reliable injection for any
  future "prove the PII scan actually fires" check.
- **AI-text-detector model swapped mid-implementation**: the originally-assumed
  `openai-community/roberta-base-openai-detector` (GPT-2-era) empirically failed on
  real Claude-generated CVs — scored genuinely-AI-written text at ~0.0002 "AI-generated"
  probability (backwards). Replaced with `desklib/ai-text-detector-v1.01` (leads the
  public RAID benchmark, validated against modern-LLM output, MIT license) in
  `data/ai_text_detector.py`. Two bugs fixed in that model's own model-card example
  code: `self.init_weights()` → `self.post_init()` (needed for `transformers>=5.x`)
  and `padding="max_length"` → `padding=True` (~6.5x speedup at batch size 1; batching
  multiple docs together was measured *slower*, not faster — mixed-length docs pad up
  to the batch's longest, undoing the per-item win — don't add batching). Even fixed,
  expect ~10-15s/doc on CPU (DeBERTa-v3-large, no ONNX/quantization) — accepted as fine
  since dataset labeling is offline/one-time per specs §5, not latency-sensitive.

## Context

`specs/20260918-mvp.md` specifies the full JobFit MVP: a client-side CV/JD fit-scoring model (CQR head on a repurposed causal LLM backbone), an offline synthetic-dataset toolset, a K8s/Argo training pipeline with MLflow tracking, and a Vue3 SPA doing in-browser inference via transformers.js. The repo is brand new — only `.gitignore`, `README.md`, `specs/20260918-mvp.md`, and `data/fetch_jobs/` exist. Everything else in §8's layout (`datasets/`, `aspects.json`, `pipeline/`, `frontend/`, `infra/`, `docker/`, `reports/`) is created from scratch.

`.gitignore` already excludes weight files (`*.onnx`, `*.safetensors`, etc.) — §10's "no shipped weights" holds already, no new work needed.

`data/fetch_jobs/` was read in full and is functionally complete — every fetcher/discoverer matches §8's layout, no stubs or bugs. The one defect, flagged by spec §12 itself, is `common.py`'s spoofed browser `USER_AGENT` sent to plain JSON APIs.

**Decisions binding this plan:**
- **User-Agent**: replace with a descriptive one, `JobFit/0.1 (+https://github.com/<org>/jobfit)`.
- **Redistribution licensing** (§12): proceed with fetching/committing now; ToS review is a gate before going public, not before development.
- **LLM calls**: `generate_cvs.py` and `label_dataset.py` shell out to `claude -p` (structured output) instead of a separate billed provider API.
- **GPU / HF Hub push**: deferred to a separately-approved decision at Phase 7. Everything else runs free/local.
- **Docker**: additive only — new image/container/cluster names, never touching unrelated running containers (`docker ps` before/after infra steps).
- **Tests**: real-data smoke tests by default. Plain unit tests only for pure, dependency-free logic (string helpers, split-grouping logic, a UI component given a hardcoded prop) — no mocking of network/subprocess/model calls.
- **Directories**: this pass's small real corpus (10 CVs, 10 jobs, see Status above) lives in `datasets_smoke/` (committed to git — see Phase 5), never `datasets/` — which stays reserved for the real, eventually-committed full-scale corpus. Every dataset script takes a `--out-dir` (default `datasets/`, overridden here; `data/fetch_jobs/`'s `--out-dir` default is `datasets/jobs` specifically, since its out-dir *is* the jobs directory itself, not the dataset root — the others take the dataset root and write their own subdir under it).
- **PII scrub scope** (refined during Phase 2): Presidio's generic `PERSON`/`ORGANIZATION`/`LOCATION`/`DATE_TIME` recognizers are too noisy on CV/JD text (flagged "Python", "Docker" as `ORGANIZATION` at a flat 0.85 — every CV inherently has *a* name/employer/date, that's not a leak). `data/pii_scrub.py` scopes to unambiguous-if-present entity types only: `EMAIL_ADDRESS, PHONE_NUMBER, CREDIT_CARD, US_SSN, IBAN_CODE, IP_ADDRESS, CRYPTO, US_DRIVER_LICENSE, US_PASSPORT, MEDICAL_LICENSE`. The deliberately-fake `firstname.lastname@example.com` contact pattern `generate_cvs.py` asks for is whitelisted.
- **AI-text-detector model** (refined during Phase 4, see Status above): `desklib/ai-text-detector-v1.01`, not `roberta-base-openai-detector` — the latter empirically can't detect modern (Claude-era) LLM text.
- **Double-labeling QC scope** (extended during Phase 4, on user request): covers `cvs.jsonl`/`jobs.jsonl` too, not just `pairs.jsonl` — `--double-label` now also writes `cvs_double.jsonl`/`jobs_double.jsonl`, re-judging `clarity_score` (the only judge-scored field in those files) for the same CVs/jobs referenced by the sampled double-labeled pairs, with the second judge model. The detector-derived `llm_generated_score` is not re-run there since it's deterministic — a second call would just repeat the same number.

**Notable findings** (bugs hit and fixed while getting to the run above)
- `pipeline/prepare.py`'s `encode_pair` padded with a literal `0` instead of the tokenizer's real `pad_token_id`. HF's `*ForSequenceClassification.forward` locates the pooled token via `input_ids != config.pad_token_id`, not `attention_mask` — wrong padding silently pools a padding position instead of the real last token. Fixed by threading the real `pad_token_id` through.
- `pipeline/common.py`'s `backbone_state_dict_hash` called `.tolist()` on every backbone parameter tensor — on a 596M-parameter backbone this materializes hundreds of millions of individual Python floats, tens of GB of pure interpreter overhead, killing the process (OOM, exit 137) independent of the actual training loop. Fixed by hashing raw tensor bytes (`param.detach().cpu().float().numpy().tobytes()`), with a `.tolist()` fallback retained only for a duck-typed test double lacking `.detach()`.
- bf16 on this class of CPU (no AVX512-BF16) runs through a slow emulated path — a `bf16` `headtrain` run burned 25+ minutes without completing a single tiny epoch despite genuine ~7-8x CPU parallelism. Switched `common.load_classification_model` to `dtype=torch.float32`, which is well-optimized on any CPU.
- `pipeline/finetune/finetune.py`'s LoRA adapters sit at every transformer layer, so — unlike `headtrain`'s frozen backbone, which builds no autograd graph at all — gradients must flow back through every intervening frozen layer, forcing full-depth activation memory comparable to full fine-tuning (OOM, exit 137, even at batch size 1). Fixed by enabling gradient checkpointing on the base model before LoRA-wrapping it (`gradient_checkpointing_enable(gradient_checkpointing_kwargs={"use_reentrant": False})` + `enable_input_require_grads()` — the latter is required, since checkpointing on an all-frozen-backbone model can otherwise silently break the gradient graph). Confirmed fixed end-to-end by the real `finetune` run above (step 3).
- `pipeline/export/export.py`'s `ORTQuantizer` output is named `model_quantized.onnx`, not the `optimum` default `model.onnx`; `ORTModelForSequenceClassification.from_pretrained()` logs a "could not find standard file name" warning but still auto-selects the single `.onnx` file present and loads correctly — harmless, not a bug, but worth knowing so the warning isn't mistaken for a failure.
- **Real bug, found in review**: `pipeline/workflow.yaml`'s (and the Makefile's `smoke-export`'s) `evaluate-quantized` step pointed `--calibration-params` at `export/<slug>/calibration.json` — the *re-fit* (post-quant) params — instead of the unchanged pre-quant `calibration/<slug>/params.json`, so the DAG never produced the "does quantization break calibration" comparison §4 requires. Fixed in both places. Confirmed the two files' deltas genuinely differ (e.g. `skills_match`: pre-quant `-0.249` vs. refit `1.305`), so this was a real, not cosmetic, wiring bug.
- **Also found in review**: several spec-named MLflow practices (§6: `autolog()`, `log_input()`, registry aliases, `infer_signature()` beyond `headtrain`) were missing. Added `mlflow.transformers.autolog()` to `headtrain`/`finetune` (the two training stages); `mlflow.log_input()` dataset lineage to every stage that reads a cached split; `common.log_model_signature()` (refactored out of `headtrain`'s inline version) to `finetune` and `export`; and `champion`-alias model registry registration to `publish`. Also added the OTel `stage_span` that `prepare.py` was missing, and an actual `gpu_utilization_percent` gauge metric (0 on this CPU-only host) — the otel-collector config referenced this metric in a comment before it existed in code. All confirmed via a second real end-to-end run (new MLflow run IDs, registered model `jobfit-qwen3-0.6b` v1 aliased `champion`).

**Inputs/runs/output cleanup (on user review of this pass, done in four steps, each answering the next question the previous one raised)**

*Step 1*: `datasets_smoke/` had accumulated `cache/`/`checkpoints/`/`calibration/`/`eval/`/`export/` alongside the committed corpus (`cvs/`/`jobs/`/`labels/`/`splits/`) — every pipeline stage from Phase 6/7 wrote its output into the same `--dataset-dir` it read the corpus from, and 43 of those output files (tokenizer/config copies, eval/calibration JSON — not the gitignored weight binaries) had ended up committed. This doesn't match specs §5, which only ever calls for `datasets/`'s four subdirectories. Fixed: every pipeline stage script (`prepare`/`headtrain`/`finetune`/`calibrate`/`evaluate`/`export`/`publish`) took a separate `--artifacts-dir` for its own scratch/output, `--dataset-dir` mounted/treated read-only from `prepare` onward.

*Step 2 ("is a report an artifact too?")*: yes, `reports/<sha>-<slug>.json` is also pipeline-generated output, not raw input, so leaving it as a same-named-but-conceptually-different top-level directory (`reports/` next to `artifacts/`) was its own inconsistency, and `report_writeup.py` living inside `reports/` compounded it (code next to the output it generates). Resolved by treating "artifact" and "committed output" as the same tree with one deliberately-committed exception, not two separate top-level directories: `reports/` moved inside the (renamed) runs tree, the *only* subdirectory under `--runs-dir` that's committed, because it's the durable cross-host record specs §6 requires (MLflow's hostPath PV doesn't survive the host changes specs §7 allows). Renamed `--artifacts-dir` → `--runs-dir` (`artifacts/`→`runs/`, `artifacts_smoke/`→`runs_smoke/`) at the same time: "artifact" had become ambiguous once `reports/` was itself acknowledged as an artifact, whereas "runs" (one directory holding everything a pipeline run produces, MLOps-conventional) doesn't have that collision.

*Step 3 ("what about a per-run id, `runs_smoke/<run-id>/...`?")*: considered and rejected — MLflow already assigns a real unique id per stage run (`run.info.run_id`, nestable via `--mlflow-parent-run-id`) and is the system of record for comparing hyperparameter-sweep variants (specs §4/§6: manual reruns with different LoRA rank/alpha/lr), independent of the filesystem; threading a second, redundant run-id through every stage script's CLI, the Makefile, and the Argo DAG's workflow parameters would buy nothing that isn't already covered. Landed on **`<slug>` first** instead (`runs(_smoke)/<slug>/{cache,checkpoints,calibration,eval,export,reports}`) — `slug` is already computed by every stage script (`common.model_slug()`), so this needed no new identifier, and it fixes the one remaining inconsistency from step 2: `reports/` had become the *only* subdirectory not grouped by candidate (it was flat, `<sha>-<slug>.json`, slug baked into the filename instead of the directory structure). `slug` was deliberately kept as just the base model id (`qwen3-0.6b`), not made more specific (e.g. hyperparameter-qualified) — same reasoning as rejecting a run-id: a hyperparameter rerun overwriting the previous run's scratch checkpoints is fine, since MLflow already retains that run's params/metrics regardless of what happens on disk.

*Step 4 ("the filenames inside reports/ are still too verbose, no need for a run-id there either")*: agreed — once `reports/` was nested under `<slug>/`, the `<sha>-<slug>.json`/`-thresholds.json`/`.md` filenames were carrying two redundant identifiers: `<slug>` (already the parent directory) and `<sha>` (already recorded inside the JSON body's own `git_sha` field, *and* already the identifier `git log`/`git diff` use for this exact path once it's committed — a rerun overwriting `report.json` in place is precisely what makes `git diff` a meaningful "did anything change" check). Renamed to plain `report.json`, `thresholds.json`, `report.md`.
